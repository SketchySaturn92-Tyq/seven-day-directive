# 《苏丹的游戏》剧情阅读器 · 逆向解读

站点：https://sudans-game-reader.pages.dev/
解读方式：抓取前端产物，还原其数据结构与内容组织方式。
用途：学习它的做法，对照改进《七日指令》。**只学结构与手法，不搬用其文本内容。**

---

## 一、它是什么

一个纯静态的剧情阅读器。用 Vue 打成单页应用，部署在 Cloudflare Pages。

关键观察：

- **没有后端，没有接口**。首页 HTML 只有 691 字节，真正的数据全部内嵌在
  `js/app.<hash>.js` 里，这个文件 **14.9 MB**。
- 数据被 webpack 包成一个个模块函数，形如 `42531:function(n){n.exports='[...]'}`，
  每个模块就是一段 JSON 字符串。所以**改数据等于改代码**，但好处是零依赖、纯静态、可离线。
- 阅读器自己是个查看器：把游戏运行时的内部数据结构原样摊开给人看。

对我们的意义：这种「数据内嵌 + 纯静态」的路子我们已经走通了（`game/bundle.js`）。
它的真正价值不在部署方式，而在**数据怎么组织**。

## 二、数据分了哪几层

从高频字段看，共四条线：

### 1. 事件 / 仪式条目

```json
{ "id": 5000001, "name": "治理家业",
  "text": "人们仍然愿意来到你的屋檐下，分享言语、允诺，与机会。",
  "type": "rite" }
```

`name` 2700 次、`text` 2658 次、`type` 2658 次。这是最基础的一层：一件事的标题、描述、归类。

### 2. 条件分支（核心）

```json
{ "key": "2000082_extra_1",
  "condition": {
    "counter.7000449小于": 1,
    "have.2000172.正当性": 1,
    "have.主角.苏丹": 1,
    "have.2000082": 1,
    "have.2000082.晋升": 1,
    "have.2000082.贵族": 1
  },
  "result_text": "夏玛当然能够胜任你给她的岗位……" }
```

共 **1379 条**。注意三件事：

- **条件是可读的键值对**，不是代码。`counter.X小于`、`have.对象.状态`。
  策划能直接手写，不需要程序员转译。
- **多键并列即「与」**。上面那条要求同时满足六个条件才给这段文本。
- **结果文本挂在条件上**，而不是写在流程里。同一件事，不同前置状态下读到不同的结果。

### 3. 角色档案

```json
{ "id": 2000082, "name": "夏玛", "prior": [],
  "extra": [ { "key": "...", "condition": {...}, "result_text": "..." } ] }
```

`prior` 是前置，`extra` 是这名角色身上可以追加的后续文本。角色不是一个静态介绍页，
而是**一叠按条件解锁的片段**。

### 4. 卡槽 / 目标位

```json
{ "condition": { "type": "sudan", "征服": 1, "稀有度小于等于": "铜" },
  "open_adsorb": 0, "is_key": 0, "is_empty": 1, "is_enemy": 0,
  "text": "你可以抵消一张青铜及以下品质的征服卡" }
```

卡槽自己带条件、带状态位（是否关键、是否空、是否敌对）、带说明文本。

## 三、条件表达式系统（最值得学的一块）

这是整个设计里最工程化也最好用的部分。词族统计：

| 前缀 | 出现次数 | 含义 |
|---|---|---|
| `have` | 4863 | 是否拥有某物 / 某人处于某状态 |
| `counter` | 3291 | 一个计数器的数值比较 |
| `table_have` | 66 | 桌上是否有某张牌 / 某个对象 |

### 比较运算符

`counter.<id>大于`（4787）、`counter.<id>小于`（3889）、`counter.<id>等于`（82）。

只有三个，够用。没有 `>=`、`!=` 这类，把布尔逻辑压到最小。

### `have.<对象>.<状态>` 的状态词表

按热度：苏丹、晋升、正当性、宰相、邪恶化身、命运的羁绊、追随者、激情、新妻、
幽秘的爱意、侧室、目的地、被献祭、被牺牲、被驱逐。

看这批词就能看出这个游戏的骨架：**权力头衔（苏丹/宰相）+ 情感关系（新妻/侧室/激情）
+ 命运标记（邪恶化身/命运的羁绊）+ 结局状态（被献祭/被牺牲/被驱逐）**。
条件系统不是给程序员用的，是给**叙事结构**用的。

### 给我们的启示

我们现在的 `when` 是这样的：

```js
when: { minFolded: 5, minRel: 2 }
```

方向对，但表达能力还不够。可以扩成两族：

```js
when: {
  stat:   { folded: [5, 12], day: [3, 99] },      // 数值区间
  have:   ['has_ledger', 'trusted_su'],            // 剧情标记
  track:  { sin: [7, 12], loyalty: [0, 3] },       // 名望区间
  not:    ['broke_flow'],                          // 排斥
}
```

好处是：策划写内容时不用碰引擎，改一个条件字符串就能调触发时机。

## 四、台词系统

命名规律：

```
pop.<卡ID>_<结果阶段>_<序号>.<说话人槽>
```

实例：

```
pop.5001001_result_01_1.s2
pop.5001001_result_04_2.s2
pop.5001001_result_05_1.s2
pop.<卡ID>_<阶段>_<序号>.self     ← 玩家自己说的话
```

共 **1399 条唯一键**。

三个设计点：

1. **同一件事按「结果阶段 + 序号」挂多组台词**。一次交互不是一句话，而是一串。
2. **最后一段是说话人槽位**。`.s2` 是第二个说话人，`.self` 是玩家自己。
   这样一段对话可以自然地在多个角色之间来回。
3. **键名自带结构**，不依赖顺序数组。想插一句就加一个键。

对照我们：现在的台词是 `low / mid / high` 三层各四句，按关系值抽一句。
粒度比它粗。可以学的是**把「随机抽一句」换成「按阶段串一组」**——
同一场对话里，先铺垫、再给信息、最后留后手，三句话连起来读。

## 五、富文本与内联术语

正文里不是纯文本，带内联标记：

```html
<b>…</b>
<color=white>…</color>
<color=#74E0C5>…</color>
<size=…>…</size>
<sprite …>          ← 内嵌小图标
<indent>…</indent>
```

而正文里出现的**方括号术语**：

```
【战斗】【体魄】【情报】【社交】【智慧】【魅力】【隐匿】【生存】【魔力】
【金币】【治理家业】【俺寻思】【权力的游戏】【邪术的痕迹】
```

这是**把机制名直接写进叙事句子里**。例句：

> 你该意识到，以你目前的**【体魄】**和**【战斗】**能力，你需要更多的准备。

玩家不用去查面板，读到这句话就知道该升级什么。

对照我们：我们的正文目前是**百分百纯文本**，玩家读到「罪痕」要去面板找数字。
这一步可以直接抄：把名望与资源做成内联标记，正文里出现时高亮。

## 六、阅读器的界面组织

组件清单（从代码里提取到的真实命名）：

```
EventDetails / EventDetailsModal      事件详情
EventTreeNode                         事件树节点
SlotDisplay / SlotDetailsModal        卡槽展示
CardDetailsModal / CardCondition      卡牌详情与条件
ConditionDisplay / ConditionItem / AnyCondition   条件展示
ResultDisplay                         结果展示
ActionDisplay                         动作展示
ItemListDisplay / LootDetailsModal    掉落展示
RiteDetailsModal                      仪式详情
OverDetails / OverDetailsModal        结算详情
AfterStoryDetails / AfterStoryDetailsModal       后日谈
SlotRestriction                       卡槽限制
```

几个值得注意的地方：

1. **条件和结果分成两个组件**。玩家一眼能分清「什么情况下」和「会发生什么」。
2. **有 `EventTreeNode`**，说明事件是**树状**的：一个事件可以有后续分支。
3. **有 `SlotRestriction`**，专门展示「这张牌能指向谁」的限制。
4. **有 `AfterStoryDetails`**，独立的「后日谈」层——正片之外还有收尾叙述。
5. 支持展开/收起（`expandedSlots` / `expandedOptions`），信息量大的时候不糊一整屏。

对照我们：剧情面板现在是「正文 + 选项」两段。可以补的是：
- 把这段剧情**为什么触发**用一行小字标出来（学 `ConditionDisplay`）
- 结算结果**单独成区**，跟正文视觉上分开（学 `ResultDisplay`）
- 结局后加一层**后日谈**（学 `AfterStoryDetails`）——这正好对应我们终局只有一段文案的问题

## 七、可直接落地的五条

按性价比排序：

**1. 正文内联高亮。**
把「罪痕」「忠诚」「信用点」「指令芯片」等做成内联标记，正文出现即高亮。
改动小，观感提升明显。

**2. 台词串成一段，而不是抽一句。**
现在同一 NPC 每次搭话抽一层里的一句，读起来是散点。
改成「铺垫 → 信息 → 后手」三句连读，人物立刻立体。

**3. 条件表达式扩成 `have / stat / track / not` 四族。**
让写剧情的人不用改引擎就能控制触发时机。

**4. 剧情面板加「触发条件」小字。**
学 `ConditionDisplay`：告诉玩家这段为什么现在发生。
这直接回应了「不懂世界观、不知道自己在干嘛」的反馈。

**5. 结局后加后日谈。**
学 `AfterStoryDetails`。我们 17 个结局目前只有一段文案，
加一层「后来发生了什么」，把余韵拉长。

## 八、边界说明

- 该站点是**他人作品的剧情数据**。本解读只提取了结构、字段名、组件命名、统计特征，
  以及少量作为格式示例的短句。**没有、也不会**把它的正文搬进《七日指令》。
- 《七日指令》的题材、世界观、人物、文本全部为原创。
- 可学的是工程手法与叙事组织方式，这部分属于通用设计经验。
